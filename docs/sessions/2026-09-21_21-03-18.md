## 任务 2：曲谱视图「简谱与歌词错位」+「最大化后不水平居中」修复

### 提问

> ① 程序启动后曲谱显示区截图：简谱和歌词错位；
> ② 程序最大化后截图：曲谱显示区内容没有水平居中。

### 解决思路

1. **先定位错位来源**：两张截图均来自任务 6 新增的「PPT 原生渲染」视图
   （`ppt_score_view.dart`，逐行 `TextPainter` + 编码串自然 advance）。
   核对第 1 首：谱行 `1  1    3  3 \ 5/5/\…`（无前导空格）、歌词行 `  圣哉，…`（2 个前导空格）
   → 歌词首字相对首个音符右移 2 谱 em（≈ 1 个歌词字宽），与用户目视「错位」一致。
2. **验证 PPT 侧能否修正**：
   - 解析 PPT 段落级水平基准（`ClientAnchor` / `TextPFException.indent`）→ 本次解析拿不到（None），
     无法判定两行是否同框同缩进；
   - 因此改为「用 PDF 精确对位反推 PPT 字形」的混合方案（新写 `tools/align_ppt_glyphs.py`）：
     逐行/整曲把 PDF 音符序列与 PPT 编码字形序列对齐，音级零不符才写回 `disp_seq`。
   - 全库实测：PDF 主旋律行 3184 条中，**音符总量与某 PPT 页一致的仅 12 首**；结构键匹配 271 行；
     严格「音级零不符」验收仅 **300/3184（9.4%）**；对「PPT 字形→PDF 音级」做统计时出现系统性冲突
     （如 `E` 先验 3 vs 多数配对 5），说明余下配对掺错行 → 若写库会**引入错误音级**。
     **判定：全库层面无法安全推导映射，放弃该路径。**（`disp_seq` 最终未写入，DB 结构未变。）
3. **定稿**：显示链路回退到任务 5 已验证的 **PDF 精确对位渲染**（`ScoreLyricPageView`：
   列宽 = 可用宽 / 最宽谱行元素数，一元素一列，歌词按第 1 节 `note_index` 真值落列，其余节按字序落同一套列位）
   —— 该方案天然解决两问题：**逐列对位**（不再错位）与**列网格铺满可用宽 + 标题居中**（不再左堆）。
4. **顺手升级歌词字体**：印刷 PDF 内嵌字体清单含 `¼Ð·¢Åé`（標楷體）与 `MMP2005`（简谱字体），
   与官方 PPT 的「歌词字体.ttf = 標楷體」同源 → 曲谱视图歌词改用内嵌 `EchoKai`，
   fallback `KaiTi` → `EchoSans`（更贴近印刷本/投影）。
5. **清理回退项**：删除 `ppt_score_view.dart`、`hymn_ppt.dart` 模型、`repo.loadPptDoc/hasPptTables`、
   `JianPu` 字体声明与 `assets/fonts/jianpu.ttf`、14 条 PPT 渲染用例；
   **保留** `hymn_ppt`/`hymn_ppt_line` 表、`tools/extract_ppt.py`、`lyric_kai.ttf`（数据/素材资产）。

### 最终结果

- **完成结论**：两问题均修复——歌词逐字落在对应音符列下、最大化时整页列网格铺满可用宽且标题居中。
- **关键改动**：
  - `hymn_app/lib/widgets/hymn_display.dart`：`_buildScoreLyric` 收敛为唯一 `ScoreLyricPageView`；
    移除 `_pptDoc` 状态、`loadPptDoc` 调用、PPT 页数分支。
  - `hymn_app/lib/services/sqlite_repository.dart`：移除 `loadPptDoc`/`hasPptTables`，保留说明注释。
  - `hymn_app/lib/widgets/score_lyric_view.dart`：歌词 `TextStyle` 增加 `fontFamily: 'EchoKai'`
    （+fallback）。
  - `hymn_app/pubspec.yaml`：移除 `JianPu` 字体族；保留 `EchoKai`。
  - 删除：`lib/widgets/ppt_score_view.dart`、`lib/models/hymn_ppt.dart`、`test/ppt_score_test.dart`、
    `assets/fonts/jianpu.ttf`、`tools/align_ppt_glyphs.py`（原型，未采纳）与本次全部临时调试脚本。
  - 文档：`docs/Windows/UI_CONFIRMATION.md` §5.15 加回退声明 + 新增 §5.16 定稿与实证数据。
- **验证方式**：`flutter analyze` 无问题；`flutter test` **45/45** 通过；
  `flutter build windows --release` 成功；实机截图两档窗口（900×640、2048×1120 最大化）目视核对
  （第 1 首：圣/哉/圣/哉… 各归其位；最大化无右侧空白带，标题居中）。
- **遇到的困难**：① PPT 侧段落级水平基准取不到，编码串空格与 PDF 音符 x 无法互推；
  ② 两套数据行切分粒度不同（PDF 一行 = PPT 两行）、且 PDF 旧行存在 ±1~2 音符噪声，
  使「逐字映射」在全库层面不可靠 → 最终选择「以已验证对位为准，PPT 编码只作数据资产」。
- **遗留问题**：若要恢复「PPT 编码原生渲染」（收益：时值下划线/连音线弧字体原生），
  需先拿到 PPT 段落级基准（解析 `TextPFException`/`ClientAnchor`，或从导出的 PDF 逐字符 x 反推每行 indent），
  或按每首建立「PDF 元素 ↔ PPT 元素」映射表（专项工作量）。

## 任务 4：曲谱视图改「字体原生渲染」（内置记谱字体）+ 歌词页去「第 N 首」

### 提问

1. 曲谱播放方式，肉眼可见还是不行，是否可以将 PPT 的内容直接作为 data 的资源，自动安装字体，
   直接在播放器中播放；
2. 歌词播放方式，「第 N 首」的标题不要了，因为标题栏已经有相关信息了。

### 解决思路

1. **先取证「为什么原方案肉眼可见不行」**：打开 hymn 1 的 `1_简谱.pdf` 与实机截图逐项比对——
   PDF 页内 **27 张 image、0 条矢量绘制**：印刷乐谱是**位图**，上面盖一层**隐藏文本层**
   （逐字形 origin 一致 0.25em 间距 → advance 被压平，只能检索不能排版）。
   原实现靠「码本 + 自绘几何」近似，**必然在连音弧（此前映射为空串 → 占一个空列，肉眼是断口）、
   时值线粗细/位置、附点大小等处露馅** ——结论：换渲染方式，而不是继续修补几何。
2. **验证用户建议的可行性（等价路径）**：抽出内嵌 **MMP2005** 字体量化——
   **字形本身就是预合成装饰**（`4ef0`=5̲、`4e4d`=低音5、`4e5e`=1̇、`5d3d`=附点、`602d`=小节线、
   `5e66~5e6e`=连音弧 1.7~3.7em），而库内 `code_seq` 正是这套码位序列（前一轮已逐元素核验）。
   → **同字体渲染同码位串 = 印刷记号**，装饰全部自带，不需要再自绘，也不需要 3GB 的 PPT 素材。
3. **方案对比**：① 把 PPT 文件当资源、播放 PPT 幻灯片（Flutter 无 PPT 渲染器，需离线转图 ✗）；
   ② 系统级安装字体（写系统字体目录 + 注册表，需管理员权限、有副作用 ✗）；
   ③ **内置字体 + 播放器内字体原生渲染**（无副作用、矢量、可缩放 ✓）→ 取 ③，并把
   `hymn_score_line.code_seq`（已在库内、已核验）当作「PPT 内容」的数据源。
4. **合并字体的必要性与做法**：每页 PDF 的内嵌子集只含该页字形（第 1 首页只覆盖 74/80 个码位），
   且 advance 被压平 → 写 `tools/build_jianpu_font.py`：遍历 475 份 PDF 抽子集（406 份去重）→
   以覆盖最优者为基底**跨文件合并字形**（含复合字形递归、cmap/hmtx/maxp 同步）→ 输出
   字体资产 + **字形墨迹度量表**（墨迹宽/xMin/yMin/yMax，em）——因为 advance 不可用，
   版面只能用墨迹宽度来排。
5. **排版比例从印刷页实测（不靠猜）**：hymn 1 位图 200dpi 分析得
   槽距 24.9pt、记谱字号 24.6pt、歌词 12.6pt → **槽距 = 1.0 S、歌词 = 0.50 S**（此前实现恰好相反：
   音符≈歌词大小）。另外：连音弧不占槽位（覆盖绘制）、小节线按行带裁剪

### 最终结果

- **改了什么文件**
  - 新增 `tools/build_jianpu_font.py`（跨 PDF 合并记谱字体 + 生成度量表，可重跑）；
  - 新增 `hymn_app/assets/fonts/jianpu_mmp2005.ttf`（64.4 KB，family `EchoJianpu`）、
    `hymn_app/lib/data/jianpu_metrics.dart`（80 码位度量，生成物）、
    `hymn_app/lib/models/jianpu_layout.dart`（字形/元素/行盒模型）；
  - `hymn_app/lib/widgets/score_lyric_view.dart`：`_ScoreLinePainter` 字体原生绘制，
    删除 `_GlyphDeco`/`_SymCell`/`_SymPainter` 全部自绘几何；版式常量（槽距/歌词比/行距）集中注释；
  - `hymn_app/lib/models/hymn_score.dart`：`ScoreLineRow.tokens`；`services/sqlite_repository.dart` 装配 tokens；
  - `hymn_app/pubspec.yaml`：注册 `EchoJianpu`；
  - `hymn_app/lib/widgets/hymn_display.dart`：歌词页删除「第 N 首」（行数预算 3 → 2）；
  - `hymn_app/test/lyric_page_score_test.dart`：+6 用例（字体资源/码位覆盖/装饰来自字形/
    小节线裁剪/连音弧覆盖/行盒度量）。
- **验证了什么**
  - `flutter analyze` 全绿；`flutter test` **53/53**；`flutter build windows --release` 通过；
  - 实机最大化截图第 **1 / 2 / 24 / 100 / 111** 首：连音弧（第 111 首多处）、双时值线（第 24 首）、
    低·高音点、附点、小节线全部**原生呈现**且与印刷页样式一致；歌词按列位逐字对位、标点作侧标；
    副歌行蓝色；歌词模式第 12 首确认**无「第 N 首」**。

  - 生成器最初用 `%+.4f` 输出 `+0.0430`，Dart 数值字面量不接受前置 `+` → 编译报 500+ 错，改 `%.4f`；
  - 子集字体 advance 全为 0.25em → 只能改用**墨迹度量**排版（并在设计里让「装饰不占槽位、
    小节线按行带裁剪」补偿字形跨系高度的问题）；
  - 判据取舍：`601d` 同为「|」但只有 0.46em 高（单行短竖线）→ 不按小节线裁剪，

## 任务 5：第 349 首「有简谱 PDF、无曲谱数据」根因排查

### 提问

> 第 349 首诗歌，有简谱 PDF 文档，没有曲谱数据的原因是什么？

### 解决思路

1. **先看数据面**：`hymn_score` 473 行；`tjc_hymn` 474 首，**唯一缺口就是 349**
   （`SELECT hymn_number FROM tjc_hymn WHERE hymn_number NOT IN (SELECT hymn_number FROM hymn_score)` → `['349']`）；
   349 的 `tjc_hymn` 记录本身完好（`download_status=completed`、`integrity_status=passed`、

2. **查素材侧是否异常**：`data/Hymn_Downloads` 里 349 号有**两份不同标题**的简谱：
   - `354_349奇妙的耶穌/`（DB 现用；简谱 PDF 190 KB、PNG 1640×2146）

3. **查 PDF 本身（决定性证据）**：打开 `354_349奇妙的耶穌/349_简谱.pdf` 与同库标准件对比：

   | 项 | 标准件（如 348/350） | 349「奇妙的耶穌」 |

   | API 来源 | `…/storage/uploads/hymn/score/num/<首号>.pdf` | **`…/score/c46393301f6b544e0bdf62f820f59d78.pdf`（哈希命名的上传件）** |

   **从旧「救主正在等候」换成了新「奇妙的耶穌」**，旧素材留在本地但未入库（也不可用于补 349 的数据）。

## 任务 6：第 349 首曲谱补录（非标版式件）+「曲谱」无数据回退整页简谱

### 提问

> 第 349 首诗歌：UI 兜底 + 走非标 PDF 抽取分支，把 349 的音符真数据补进 hymn_score。

### 解决思路

1. **先量清版式**（`page.get_texttrace()` + `get_drawings()` + `get_bboxlog()`）：该首非标件把同一套简谱记号拆成三种来源——
   音符/附点（`·` U+00B7）/八度点（`•` U+2022）在**隐藏文本层**；时值线（0.75pt 高矩形，单/双各一条）与
   小节线（高 21.7pt 竖线）是**矢量**；歌词/标题是 **Type3 轮廓字体**且**字形码 = Unicode 码位**；连音弧为矢量曲线。
2. **码位对照必须实测而非推断**：把候选项用 App 内置字体（`EchoJianpu`）逐个渲染成 150px 大图与 PDF 印样并排比对，
   钉死 `4e4d`=低音5、`4edf`=低音5+单线、`4f56`=低音5+双线、`4ef0`=中音5+单线、`4ee4`=中音1+单线、
   `4f59`=中音1+双线、`5d3d`=附点、`602d`=小节线（`DOCS/sessions` 与 `_shots/proof_big.png` 留痕）。
   顺带发现：库内 `hymn_codepoint_map` 对「低音+单线」一族（`4eda`…）标注为「中音+单线」是**错的**（按字形墨迹深度可判），
   本次按字形选用，未改库内映射表（留作后续统一修正项）。
3. **歌词两处坑**：① 印刷件把「日/子/黑/長/十/心」编码成**康熙部首**（U+2F47…）与 **CJK 部首补充块**（U+2ED1 ⻑，
   无 NFKC 映射）→ NFKC 归一 + 部首补表；② 同一歌词行的字形 y 会抖动 0.5pt（把一行拆成两行）→ 改为 3.5pt 聚类容差。
   最后加**切片自校正**：该行文本必是官网歌词的连续切片，按此做确定性收敛（10 行全部零未对齐）。
4. **对位与写库**：逐字对位按几何（字心 vs 元素心，实测最大偏差 1.1pt）；`notes`/`notes_core` 口径对齐库内既有数据

## 会话总结

- 本次共处理 6 个任务（tools 清理；曲谱错位/居中修复；第二轮五条反馈；三轮反馈——字体原生渲染 + 歌词页去标题；
  第 349 首无曲谱数据根因排查；349 曲谱补录 + 曲谱无数据回退整页简谱）。
- 关键收获：
  1. 「数据入库」与「显示采用」应解耦——官方 PPT 编码是**权威数据**（已入库，475/3032/12674），
     但其**排版基准**（段落缩进）与 PDF 音符几何不同源，不能用编码串空格直接当对位真值；
  2. 对位真值必须选「已被用户验收过的那一套」（PDF `note_index`），替换数据源时要先证明
     「同源可映射」再改显示，否则会退化；
  3. 全库级「统计推断 + 严格验收（零不符）」是识别「映射不可行」的有效手段——
     9.4% 通过率 + 先验冲突即足以判定不可行，避免把错误音级写进库；
  4. **遇到「记号缺失」类问题，先查数据是否已在库**（本轮装饰码位一直在 `code_seq` 里，
     真因是映射表错标），可省掉整条采集管线；
  5. 印刷 PDF 内嵌字体的 **cmap/字形名是权威码位来源**，配合 fontTools 轮廓几何 +
     放大图目视，可把「字形 → 记号」建到可复现、可交叉验证的程度；
  6. **记号是字体的一部分**：用户提的「装字体 + 内容直接渲染」是对的方向——同字体渲染同码位串
     即等于印刷记号，比「自绘几何近似」少一整层近似误差（弧线、时值线、点全部自带）；
     代价是必须自建排版（该字体 advance 被压平 → 用字形墨迹度量排）、并跨 PDF 合并子集字形。
