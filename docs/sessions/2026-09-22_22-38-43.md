### 解决思路

**1) 取证路线选择**

| 方案 | 结论 |
| --- | --- |
| jadx 反编译读 Java 源码 | ❌ 放弃：GitHub 直连被重置、镜像 ~12KB/s |
| **adb 实机取证 + androguard 反汇编** | ✅ 选定：APK 单 `classes.dex` 纯 Java，`OneHymnActivity.showView()V` 只有 20 余条 `replaceAll`，语义完全可读 |
| WebView CDP（Chrome DevTools 协议）调试 DOM | ❌ 不可用：应用非 debuggable，无 `webview_devtools` socket |

**2) 决定性取证手段的升级（本次方法学最大收获）**

`uiautomator dump` 的**无障碍树**会把 WebView 的内部结构暴露出来：

- `<table>` → `android.view.View`（宽 1043px）、`<tr>` → 子 `View`、**每个 `<td>` 也是 `View`（含空单元格！）**；
- `<img>` → `android.widget.Image`，且 **`text` 属性 = 图片文件名（即 `<img>` 的文件名/alt）**；
- 文本节点 → `text` = 单元格文字。

于是可以重建**「App 实际渲染的表格矩阵」的元素级快照**（行 × 单元格 × 坐标），
比"截图肉眼比对"硬得多，正好符合项目规则「谱面差异的判定必须用确定性证据」。

**3) 三路交叉验证**

1. **数据真值**：`assets/NNN.csv`（994 首，逗号分隔的二维网格）；
2. **算法真值**：`OneHymnActivity.showView()` 的 `replaceAll` 链（androguard 反汇编）；
3. **呈现真值**：uiautomator 无障碍树（元素级矩阵）+ 实机截图；**符号语义**再用 App 自带 `res/raw/hymn_NNN.mid` 的 MIDI 音高做独立验证。

**4) 关键判断：CSV 网格本身就是同步数据模型**

CSV 是「20~50 列 × 20~100 行」量级的二维网格（全库 474 份，中位 44 行 × 28 列），**同一列 = 同一音符位（同一拍点）**，
简谱数字、八度点/减时线/延长记号、小节线（`rowspan`）、以及**歌词音节**全部写在**同一列**里 ——
对齐在**数据**里就完成了，运行时**不做任何时间-像素换算**（这正是"同步"的全部秘密）。

#### B. 简谱页生成算法（`OneHymnActivity.showView()`，按反汇编顺序）

```text
html = 逐行读 assets/<编号>.csv（UTF-8）
html = html.replace(",R","</td></tr>")                     // 行结束
           .replace("T,",'<tr style="height:10px"><td>')   // 行开始
           .replace(",L7",'</td><td rowspan=7><img src=".../L7.png">')   // 小节线（L2~L7 递减）
           ...
           .replace(",L2",'</td><td rowspan=2><img src=".../L2.png">')
           .replace(",X","")                               // 占位（被 rowspan 覆盖的格子）
           .replace("M",'<img src="file:///android_asset/')
           .replace("N",'.png">')                          // M…N 包裹 => 一张符号图
           .replace("K",'</table><br><table ...>')         // 换页/换表
           .replace(",","</td><td>");                      // 单元格分隔
page = "<html><body>" + TABLE_OPEN + html + "</table><br><br><br><br></body></html>"
TABLE_OPEN = has_border ? '<table frame="border" rules="all">'
                        : '<table style="color:#FFFFFF;" cellpadding="0">'   // has_border 恒 false
webView.loadDataWithBaseURL(null, page, "text/html", "UTF-8", null)
```

要点：
- **没有 JS、没有 CSS 定位、没有图片绝对坐标** —— 对齐完全交给 HTML 表格的列语义；
- 空单元格 `,,` → 空的 `<td>`，仍占一列（对齐不塌陷）；
- `,X` 是"被上方 `L*` 的 `rowspan` 跨过的格子"占位符，被删除后该列由 rowspan 续占 →
  **每行有效列数恒定**（009 = 25 列；音符区 = 20 列），这是可用机器校验的**同步不变式**；
- 小节线 `L2~L7` 是「2px 宽 × 31/48/60/70/80/80px 高」的位图，`rowspan=N` 让它跨 N 行 →
  视觉上小节线只跨"音符行 + 记号行"，**不跨歌词行**（与实机截图一致）。

#### E. `E`（空心圆）到底是什么？—— 三重判定：延长记号（fermata）

1. **位图**（`sym_probe.py`，10×10 精确像素）：`E.png` = 上方**开口向下的弧线**（第 4~7 行外缘逐行扩张）+ 弧下**一个小圆点**（第 6~8 行）→ 即 **⌒ + •**；
2. **位置统计**：只出现在音符行的**上一行**（169 次 vs 3 次）；
3. **MIDI 反证**：`E` 所在音符（009 第 11/21 列 = 主旋律 `3`/`2`）在 MIDI 中音高**与相邻音同八度**（`71`/`69`，主音 67）
   → 排除"八度记号"；而 `EUD` = `E`+`UD`（延长记号 + 高八度点）能共存 → 反证 `E` 与八度记号**正交**；
4. **印刷原谱对照**：同曲五线谱页扫描图（`staff_009.gif`）在乐句末确有 fermata（⌒•）。

## 任务 2：谱面数据源切换到 APK CSV 网格（结构化入库 + 重建 EchoHymn 简谱显示）

### 提问

（用户）`data/tjc_hymn.db` 的谱面数据推倒重来：**不要 `hymn_codepoint_map` 与 `hymn_score` 相关表的数据**了，
把 APK 的 474 份 CSV 的**内容写入数据库**，然后借鉴 CSV 的「列 = 拍点」对齐逻辑**重建 EchoHymn 的简谱显示**；
重点在于「CSV 内部数据 → 现有 EchoHymn 软件的 UI 风格」，**不是照搬动态 HTML 表格**，避免单纯的黑底白字
（后续追问明确：不是把 CSV 当文件用，而是入库）。

### 解决思路

1. **编号映射先验证**：APK 474 份 CSV（`001`~`469` + 5 组甲乙变体）↔ 库内 473 首
   （`1`~`469` + `51_a/51_b`…）一一对应；唯一差异是 CSV 有 `349`（该首 2026-09-21 已按用户要求整首移出库）
   → 映射规则 `001→1`、`051a→51_a`，孤儿仅此 1 首（测试里作为预期断言）。
2. **数据结构 = 结构化落库**（不把 CSV 文件塞进 assets）：
   `jianpu_score`（一首一行）/ `jianpu_row`（一行一格，含**原样文本**便于自检）/ `jianpu_cell`（**列 = 拍点**）。
   空单元格与被小节线 `rowspan` 覆盖的占位格**不入库**（渲染按 `rowspan` 补画竖线）——库体积 41MB → 26.7MB。
3. **渲染 = 融入 EchoHymn 现有体系**（不引入 WebView/HTML）：
   - 数据：`loadJianpuScore()` → `JianpuScore`（块/行/单元格 + 小节线跨行区间）；
   - 视图：新增 `JianpuGridView` —— 列宽 = 可用宽 / 全曲最大列数（同列必然对齐）；
     配色走 `AppColors` 语义色（`lyricsBg` 底 + `textPrimary` 字 + `primary` 半透明小节线，随换肤联动）、
     字号随全局缩放等级；音符数字用内置印刷记谱字体 `EchoJianpu`，
     记号（**减时线 / 低·高音点 / 延长记号**）与小节线按数据语义**自绘**（CSV 本就把记号放在独立行列，自绘即忠实）；

## 任务 3：简谱按「一节一节」显示（咨询 → 落地）

### 提问

（用户）既然已经有了 `jianpu_*` 三表，那么诗歌按照一节一节的显示，难度大吗？

### 解决思路

先**用数据回答「节 ↔ 谱行」是什么关系**（调查脚本 `E:\apk_re_tjc\stanza_shape*.py`，仓库外）：

| 实测 | 值 |
| --- | --- |
| 「一块一节」（每块仅 1 节歌词且节号互异）的诗歌 | **0 / 474**（不存在） |
| 各块歌词节号集合完全一致的诗歌 | 194 首；不一致 280 首（= 后续块仅第 1 节，即**副歌/叠句**） |
| 每块歌词行数 | 多为 2~4 行 |
| 节数分布 | 2 节 16 / 3 节 192 / 4 节 230 / 5 节 26 / 6 节 8 / 7~8 节 2 |
| 节号标签 `(k)` | **只在每首第 1 个乐句块里出现**（其余块直接写音节，与印刷本一致） |

⇒ 结论：**「节」只是歌词行的属性（`jianpu_row.stanza_no`），旋律（谱行）被该块的所有节共用**。
所以「按节显示」只能过滤**歌词行**，谱面内容不变；「一页只显示该节谱行」在数据上不存在
（不是实现难度问题，而是结构性事实）。改动量：约 40 行 + 复用现成分页控件。

### 最终结果

- `JianpuGridView` 新增 `stanza`（`null` = 整页，保持原形态；整数 = 只显示该节）：
  过滤只作用于歌词行，谱行/记号行/小节线照旧；并新增**按高度收缩字号**（内容少时放大铺满宽度，超一屏才滚动）；
- `hymn_display.dart`：简谱模式 `_pageCount = 谱面节数` → 一页一节 + 底部「第 k / N 节」翻页条 +
  右上角「手动/自动」按钮（自动 = 复用 `autoPageIndexFor` **跟随播放切节**，与歌词页同一套逻辑）；
- 验证：`flutter analyze` **0 issues**、`flutter test` **41 passed**
  （新增「按节显示」组件测试：第 2 节视图只剩 `(2)`、`(1)`/`(3)` 不在树上、音符字形仍在 ⇒ 谱面不随节变化）；
  新增 golden `test/goldens/jianpu_009_stanza2.png` 供人工核对版式（已核对：只有第 2 节歌词，谱面完整）。
- 注意：切到某节时，若某块缺该节歌词（副歌块只写一行词），该块**只有谱行无歌词** —— 与印刷本一致，
