## 任务 4：§3.1 设计稿细化（抽屉内容 / 横屏 / 设置页 / 手势决策 / 字号档位）

### 提问

（用户四条追加要求）
1. §3.1 布局骨架内容再详细一些，**左滑出、右滑出的内容也要设计出来**，所有 UI 界面都需要设计稿；

5. Android 版**字号放大倍数不能照搬 Windows**（Windows 默认显示屏幕更大）。

### 解决思路

**（1）先取证，再设计**：读 `lib/theme/app_fonts.dart` 拿到 Windows 字号体系（`FontSizeLevel` = 1.0 / 1.3 / 1.6 / 1.9，实现为整树 `Transform.scale`，基座 850×890）；grep `home_screen.dart` / 各弹窗确认现有尺寸常量（顶栏 40、左栏 350、右栏 600、手册 560×560、歌单 520×420、搜索 640×560）。

**（2）手势冲突的技术判定**（回答问题 2）：
- Android 10+ 全面屏手势的「返回」由**屏幕左/右边缘起划**（系统保留带约 20~40dp）触发；App 若注册边缘滑动 → 一次起划会**双响应**（开抽屉 + 触发返回），Android 15+ 预测性返回还会与 App 动效打架；
- 排除方案 `View.setSystemGestureExclusionRects` 是**原生 View API**，Flutter 无公开稳定接口，且削弱系统手势体验（Play 不鼓励）→ **不采用**；
- 结论：**A 案（用户倾向）** —— 不注册任何边缘手势，抽屉/切歌/缩放全部走图标按钮；手势只保留"屏幕中部"的滚动、双指捏合、双击复位、长按，且每个手势动作都有**等价图标按钮**兜底（同时满足无障碍）。

**（3）字号重建思路**（回答问题 5）：Windows 基座 850×890 ≈ 0.76 M px，手机 412×915 ≈ 0.38 M px（约一半）→ 同系数在手机上占屏翻倍；且 Windows 是"控件一起缩放"，手机不能缩放控件（吃高度、放大热区）。故：档位 1.00/1.10/1.20/1.30（步长 0.10，上限 1.30）+ 只缩放文本（`textScaler`）+ 新增**移动版基准字号表** + 与系统字体缩放叠加封顶 1.40。

**（4）覆盖全部界面**：以文本 ASCII wireframe 补 14 张设计稿（竖屏 9 张 + 横屏 2 张 + 沉浸态 1 张 + 手势/横竖屏策略 2 张），并把设计稿内嵌进计划（不另建文件）。

## 任务 5：追加「有音频版 / 无音频版」双变体需求（2 平台 × 2 变体）

### 提问

（用户）刚想到一个关键点：Android 版本发布时，无论是手机版还是平板版，**都各自再区分成两个版本**，分别是**有音频版**、**无音频版**；**无音频版在 UI 上就没有播放音频的功能**。

### 解决思路

**（1）先量化差异**（决定方案可行性）——实测素材构成：

| 资产 | 数量 | 体积 |
| --- | --- | --- |
| `.m4a`（鋼琴版）+ `.mp3`（人聲版） | 793 + 464 | **2428.7 MB（2.37 GB）** |
| `.png`（简谱 + 五线谱扫描图） | 948 | **487.5 MB** |
| `.pdf` | 948 | 412.3 MB（Android 用不到 → 两版都排除） |
| `_misc` 杂物（`Clash…setup.exe` 等） | 3 | 47.2 MB（**必须排除**） |

→ 有音频版 ≈ **2.95 GB**；无音频版 ≈ **0.52 GB**（差 2.43 GB）。DB 侧实测 473 首 `audio_versions`/`staff_png_path`/`numbered_png_path` **100% 有值** → **两版共用同一份 DB**，无需维护两份库。

**（2）变体怎么落（方案对比）**：

| 方案 | 评估 | 结论 |
| --- | --- | --- |
| 再开 2 个 Git 分支（共 4 个） | 差异只是"功能开关 + 素材打包"，不是布局 → 分支数翻倍、同步成本高 | ❌ |
| **构建变体（Gradle flavor + `--dart-define`）+ 编译期常量** | 一个代码库、2 分支、4 产物；tree-shaking 可裁剪音频代码 | ✅ **选定** |
| 同包名不同渠道 | 两版**不能同时安装**（同 `applicationId`） | ❌（必须 4 个不同 `applicationId`） |

**（3）UI 处理原则**：不是"把按钮隐藏"，而是**重新分配空间**——播放条（72dp）与版本行（44dp）整块消失，省下的高度全给主体区；设置页「播放」分组改造为「显示」分组（屏幕常亮 + 新增**自动翻页间隔**）。

**（4）识别出 3 个必须定稿的设计缺口**（原方案直接照搬会漏）：
① **自动翻页失去时间基准**（原来依赖播放进度）→ 建议改「定时翻页」（关闭/15s/30s/60s）；
② "当前播放"语义消失 → 改「当前浏览」（顶栏副行 + 列表 ●）；

## 任务 6：三问澄清（播放进度来源 / 「当前播放」语义 / 响应系统导航键）与上一版表述更正

### 提问

1. 自动翻页失去时间基准，原因是依赖播放进度——那 Windows 版的播放进度是在哪里？怎么得到的？为啥 Android 无法实现？
2. 「当前播放」语义失效，为啥？
3. 响应系统：如果系统有导航键，那就放导航键；如果没有，那就全给主体区。

### 解决思路

**（1）先查代码，再回答**（不凭印象）：读 `audio_service.dart`（进度流）、`hymn_display.dart`（消费点）、`models/hymn.dart`（换算函数）、`app_state_service.dart`（锚点字段）。

**（2）关键更正**：上一版我写「Android 无法实现自动翻页」是**错误表述**。事实链条：
`AudioPlayer.onPositionChanged`（audioplayers L70~75）→ `AudioService._positionCtrl` → `hymn_display` 订阅为 `_pos` → `_applyAutoPage()`（L194~205）→ `autoPageIndexFor(position, totalSeconds, pageCount)`（**等分推算**）→ 页码；`totalSeconds` 优先取 **DB `audio_durations`**（L186~190）。
`audioplayers` 在 Android 走 ExoPlayer/MediaPlayer，**照常推送 position** ⇒ **有音频版自动翻页在 Android 零改动可用**；没有基准的是**无音频版**（它不播音频 → 无 position 流）。

**（3）无音频版自动翻页重定方案**：A 仅手动 / B 定时 / **C 虚拟进度（推荐）**——内部时钟模拟 position 递增到 DB 里的 `audio_durations` 总时长，**直接复用 `autoPageIndexFor`**，零新增数据、翻页节奏与有音频版逐节一致（且不出现任何播放控件）。

**（4）「当前播放」问题定性**：查证后确认**不是功能失效**，而是**命名不再贴切**。该状态承担三件事：顶栏「第 N 首《标题》」显示、列表高亮定位（测试 G10/G11）、`state.json` 锚点恢复（`hymnNumber`/`playlistIndex`/`playlistName`/`subcategory`）——无音频版**三件都仍需**，只是触发来源由"播放/切歌"变为"点选/搜索/翻页"。故**只改 UI 文案，`state.json` 字段名不动**。

**（5）响应系统导航键**：设计"双态"——有导航键（三键/二键）→ 底部放我们的「翻页 + 浏览导航条」（叠在系统栏上方，视觉连成一体）；手势导航 → **一条都不占，全给主体区**，导航入口改半透明悬浮控件 + `⋮` 菜单。判定给三层：原生 `navigation_mode`+`WindowInsetsCompat` → `MediaQuery.systemGestureInsets`/`viewPadding.bottom` → 用户设置兜底（自动/总是显示/总是隐藏）。

### 最终结果

- **完成结论**：三问全部以代码事实回答并落档；**上一版「Android 无法实现」的错误表述已更正**；无音频版自动翻页定为「方案 C 虚拟进度（推荐）」；底部导航条定为「双态 + 响应系统」。

  - §3.1.15：竖屏稿加「**仅当系统有导航键时显示**」标注；新增「**底部导航条双态设计**」（两张对照设计稿）+ 双态差异表 + **系统导航方式判定三层表** + 设置页「显示」分组新增条目（底部导航条 / 自动翻页含"跟随时长"）
