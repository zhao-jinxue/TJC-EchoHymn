## 任务 35（2026-10-25）：曲谱「放大填满」（C-8 追加，用户选 B）

### 提问

> B

（承接任务 34 末尾我列的三个选项：A 垂直居中 / B 放大填满 / C 不动）

### 解决思路

1. **先确认技术约束**：`slot = availW / colCount` —— 宽度方向**已经按列数铺满**，
   所以"放大槽宽"必然让块宽**超出可用宽**。要让字更大又不裁切，唯一办法是**加横向滚动**。
2. **只对移动端生效**：`jianpu_grid_view.dart` 是 Windows / Android 共用组件，
   桌面窗口大、放大后字会过大 → 用 `Platform.isAndroid || isIOS` 开关，桌面完全不动
   （`flutter test` 77 项含桌面渲染用例，可做回归证据）。
3. 放大系数封顶 `maxGrowScale = 2.2`（防止单句被放到荒谬的大）、槽宽封顶 `maxSlotGrow = 140`。

### 最终结果

- **完成结论：B ✅**
- **改动**（`lib/widgets/jianpu_grid_view.dart`）：
  - 新增 `maxGrowScale = 2.2` / `maxSlotGrow = 140` / `_growToFill`（仅移动端）
  - 不足一屏分支：`k = (availH / totalH).clamp(1.0, maxGrowScale)` → `slot *= k`
  - 返回结构：纵向 `SingleChildScrollView` 内**再套一层横向 `SingleChildScrollView`**，
    `ConstrainedBox(minHeight: viewH, minWidth: availW)` 保证未超宽时仍居中、超宽时可左右滑
- **验证**：`analyze` 0；`test` 77/77（桌面渲染未变）；Windows release ✓；Android overflow = 0
  - 视觉核验：内容占屏高 **1/3 → 2/3**，字号**明显更大更清晰**，右侧**无截断**，
    翻页条「第 1 / 3 节」，顶部 5 按钮完整
- **遗留**：无（`docs/Android/STATE.md` 已同步）

## 任务 37（2026-10-25）：曲谱移动端版式放开（留白 5% / 字更大）

### 提问

> 左右留白到 5% 就行，字间间距更紧凑，降到 50，字更大一些

### 解决思路

**先识别用户的三个要求在技术上互相冲突**：`slot`（槽宽）同时是「列距」「块宽」「字号基数」：
- 把 `slot` 降到 50 → 列距变小 ✓ 但**块宽也变小**（留白更大 ✗）、**字也变小**（✗）
- 实测过：沿这条路的中间版本（`maxSlot = 72`）实测留白 12%/10%、内容占屏宽仅 68%

所以不能直接照字面调 `slot`，而要**把三个目标拆到三个独立旋钮**：
1. **留白 5%** ← 块宽必须 = 可用宽。根因是「超高时压缩槽宽再居中」（`k = availH/totalH`），
   移动端改为**不压缩 + 纵向滚动**；
2. **字更大** ← 提高记谱/歌词**字号系数**（相对槽宽的倍数），不动槽宽；
3. **视觉紧凑** ← 字号变大后，列内空白自然被填掉（音符墨迹 ≈ 0.345 × 字号）。

全部**仅移动端生效**（`_isMobile`），桌面保持原常量 → 桌面 golden/测试零改动。

### 最终结果

- **完成结论：✅ 三条达标（实测）**
- **改动**（`lib/widgets/jianpu_grid_view.dart`）：
  - 新增 `_isMobile` / `maxSlotFor`（移动 320 / 桌面 72）/ `noteFontEmFor`（0.68 / 0.50）/
    `lyricFontEmFor`（0.60 / 0.54）
  - `slots` 计算、收缩分支、`_rowEm`、`_Metrics.noteSize/lyricSize` 全部改用上述 getter
  - **超高时不再压缩槽宽**（`&& !_isMobile`）→ 移动端块宽铺满、内容超出走纵向滚动
- **实测（视觉核验，1080×2400）**：
  - 左右留白 **5.5% / 6.0%**（目标 5%，达标）
  - 音符 ~**21sp**、歌词 ~**18sp**（原 ~14sp）
  - 一行完整无截断、无字符重叠、第 1 节内容不裁切、`overflow = 0`
- **验证**：`analyze` 0；`test` **77/77**（桌面口径未变）；Windows release ✓
- **可继续微调的旋钮**（若用户仍想再大/再小）：`noteFontEmFor` 0.68、`lyricFontEmFor` 0.60、`padX` 18

## 任务 38（2026-10-27）：曲谱「字看不清」根治 —— 移动端自动折行

### 提问

> （附两张截图）如果现有的曲谱歌词模式，无法复原 <参考 APK> 的效果，那就删除曲谱歌词模式…
>
> 重点不是显示一节还是全部节，而是显示的歌词内容的清晰度，明显参考 apk 显示的文字字号更大，
> 阅读更方便，而我们的 app，显示的文字很小，几乎无法看清

### 解决思路

1. **先看图再动手**：视觉模型对比两张截图 —— 参考 APK 是「一页显示全部节 + 纵向滚动」，
   我们的是「一页一节 + 翻页条」。**这一层我能复原**（`stanza: null` 整页形态一直存在），不必删功能。
2. **但用户澄清重点是字号** → 不再纠结分节，转而查字号为何小。
3. **加可测量日志**（关键一步）：把 `可用宽 / 最大列数 / 槽宽 / 字号` 打进日志，得到硬数据：
   ```
   节数 3（块数 4，最大列数 20，歌词列距 1）
   可用宽 331dp / 槽宽 16.6dp → 音符 15.7sp / 歌词 14.6sp
   ```
   → **一行 20 列 → 槽宽仅 16.6dp → 歌词 14.6sp（与正文同大）**，这就是"看不清"的根因。
4. **排除两条无效路径**：
   - 提高字号系数：歌词**列距 = 1**（每个音符都有词）→ 字宽不能超 1 列 → 系数已到 0.88 上限；
   - 缩小槽宽/加大留白：方向相反。
   → 唯一解 = **减少每行列数**。
5. **实现自动折行**：`_targetSlot = 30dp`，移动端一行最多 `floor(331/30) = 11` 列，
   超出按列区间切片（`_buildRow` 加 `colStart/colEnd`），每段按 `availW / per` 重新铺满。
   **桌面不折行**（返回原列数）→ golden 基准与 77 项测试完全不动。

### 最终结果

- **完成结论：✅ 字号提升 1.8 倍，功能保留（未删除曲谱模式）**
- **硬数据对比**：

  | 指标 | 改前 | 改后 |
  | --- | --- | --- |
  | 每行 | 20 列 | **11 列 ×2 段（折行）** |
  | 槽宽 | 16.6dp | **30.1dp** |
  | 音符 | 15.7sp | **28.6sp** |
  | 歌词 | 14.6sp | **26.5sp** |

- **改动文件**：
  - `lib/widgets/jianpu_grid_view.dart`：`_targetSlot` / `colsPerLineFor()` / `minLyricColGap()` /
    `_lyricEm()`（歌词按列距动态放大 ≤2.6em，**仅移动端**）/ `_buildRow` 加列切片 /
    `_Metrics.lyricColGap`
  - `lib/widgets/hymn_display.dart`：曲谱改回整页形态（`stanza: null`）、`_pageCount` → 1、
    移除翻页条与翻页模式按钮、日志输出真实列数/槽宽/字号
- **验证**：`analyze` 0；`test` **77/77**（桌面不折行，基准不变）；Windows release ✓；
  Android `overflow = 0`；
  视觉核验：歌词 ≈19sp+、无重叠粘连、无排版错误、一行完整无截断、明显更易读
- **遗留**：折行按列切分，可能切在小节中间（小节线仍在段内正确绘制）；
  若要求"只在整小节处折行"，需要按 `barCols` 做边界对齐（下一轮可做）

## 任务 41（2026-10-27）：折行算法重写「行数最少优先」+ 标点重叠 + 字号隔离

### 提问

> 1. 第一个"圣哉"后面的标点符号和第二个"圣哉"重叠了
> 2. 全能大主宰，看屏幕显示，应该是有足够地方显示在一行，但是成了两行，这可能是你的算法策略有问题。
>    先定最小字号，然后计算以最小字号是否能够一行显示，如果不能那就两行，然后再以两行折行显示
>    测试计算字号，能两行显示就绝三行显示，而不是无限的以大字号为主
> 3. app 设置中还有字号调整的功能，这个功能不能应用于曲谱歌词显示模式，会破坏默认的显示算法
> 4. 这种单节折行处理很好，如果算法上合适，也可以应用于 Windows 版本

### 解决思路

1. **标点重叠**：根因是歌词单元格含 2~3 个字符（「哉，」），字宽 = 0.88 槽宽 × 字符数 > 1 列
   → 必然越列。修法：`FittedBox(fit: scaleDown)` 把该格压进 1 列宽内（参考 APK 的 table 是列宽自适应，
   我们用固定列宽 + 单格缩放，效果等价且不破坏列对齐）。
2. **折行策略**：承认原实现是"固定目标槽宽（33dp）无限折行"——完全违背用户要的"行数最少优先"。
   按用户给的算法重写 `planSegments`：
   - `_minLyricSp`（最小可读字号）→ `minSlot` → `perAtMin = availW / minSlot`；
   - `perAtMin >= 块列数` ⇒ **一行**（字号最大化）；
   - 否则**按小节数均衡切分**（新增 `segmentsByBars`）—— 这一步是关键：
     旧算法按"列上限"切，遇到小节 5~6 列会切出 12/5/3 这种极不均的段，
     窄段看起来"明明能一行"；按小节数切则各段接近（4 小节 → 2 段 × 2 小节）。
   - 每段**独立铺满** `availW / 该段列数` → 消除右侧 20~30% 空白。
3. **字号隔离**：`JianpuGridView` 本身不读 `AppFonts.scale`（已确认），但系统字体缩放/上层
   `MediaQuery` 仍会影响 `Text` → 用 `MediaQuery.withNoTextScaling` 包裹曲谱。
4. **中间值实测**（不靠猜）：`_minLyricSp = 17` → 段数 8 但长块字号掉到 18.2sp（更小）；
   `26` → 段数 12、长块 26.5sp、短块一行 36sp ⇒ **取 26**。

### 最终结果

- **完成结论：✅ 四条全部落地**
- **实测**：`每行最多 11 列（共 12 段）/ 槽宽 30.1dp → 音符 28.6sp / 歌词 26.5sp`；`overflow = 0`
- **视觉核验**：**每行都是 2 小节**（均衡）、所有标点与相邻字**无重叠**、无字符截断、
  短块（「全能大主宰」类）一行显示
- **golden**：4 张因 `FittedBox` 微调（0.00%~0.21%，75~3334 px）重新生成；`test 77/77`
- **改动**：`jianpu_grid_view.dart`（`planSegments` / `segmentsByBars` / `_minLyricSp` / `FittedBox` /
  每段独立铺满）、`hymn_display.dart`（`MediaQuery.withNoTextScaling` + 日志同步）
- **Windows**：同一套 `planSegments`，`_isMobile` 开关可一键放开；当前保持桌面原版式，
  等用户试用确认后一并启用（用户已表示"算法合适可用于 Windows"）
