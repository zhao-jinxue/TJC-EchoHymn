## 任务 1：docs/Windows 新建「说明文档」（接口 / 类 / 函数），从入参视角审查并按需优化，最后补时序图 / 调用图

### 提问

用户要求：在 `docs\Windows` 下创建说明文档，包含**接口、类、函数**的说明；编辑文档时**从接口 / 类 / 函数的视角反思是否完整、是否安全**，
若发现某函数**入参不安全就优化**；文档完成后，**能编辑时序图就编辑时序图，否则创建调用图**。

### 解决思路

1. **先摸清代码**：`hymn_app/lib/**`（31 个 Dart 文件）+ `native/hymn_engine`（C ABI）+ `docs/Windows` 现有文档风格 +
   `.markdownlint.json` 规则，全部读一遍再动笔，保证文档与代码一致、可核验。
2. **文档结构**（三层契约视角）：
   - 「接口」= 本项目没有 HTTP/RPC，真正的对外契约是 **C ABI + MethodChannel + SQLite 表结构**；
   - 「类」= 按分层给每个类卡片（职责 / 关键成员 / 生命周期 / 并发与不变量 / 相关类）；
   - 「函数」= 只列**有契约价值**的函数，逐条给 `参数 / 返回 / 边界·失败 / 副作用`。
3. **安全审查**：以「入参」为切入点逐函数过——谁调用、非法参数会怎样、失败是否静默留脏数据、契约是否写明。
4. **入参优化（发现即修）**：选取**真实且低风险**的加固点——
   - `SqliteRepository` 歌单写接口此前仅在 UI 层（`TextField.maxLength` + trim）校验，**仓储层无兜底**；
   - `AudioService.playHymn/loadHymn` 的 `index` **未做越界钳制**（`playAt` 有守卫、这两个没有）。
5. **时序图可行性判定**：仓库用 Markdown，`.markdownlint.json` 已关 MD040/MD033 等，**Mermaid 代码块是合法 Markdown 且可编辑**，
   故按用户优先级**做时序图（`sequenceDiagram`）**，并**额外补调用图（`graph`）**作为静态结构补充。

## 会话总结

- 本次共处理 **1** 个任务（含文档 + 代码加固 + 测试 + 索引 + 日志）。
- 关键收获：
  1. 「说明文档」在 Flutter/Dart 项目中应以**代码级契约**为主体（接口/类/函数 + 边界/副作用），
     并从**入参视角**做安全审查，才能真正暴露问题（本次即靠此发现仓储层与播放层的入参缺口）。
  2. 入参加固遵循「**正常路径零行为变化、非法路径快速暴露**」：名称越界用截断、空名用 `ArgumentError`、
     非法 id 用告警日志——既不误伤现有 UI 流程，也不静默写脏数据。
  3. Mermaid 是 Markdown 生态下**可编辑的时序图/调用图**方案，适合直接嵌入仓库文档。
- 遗留事项：见任务 1「遗留问题」（`SEC-05` 评估、重名下沉、可选 dartdoc 接入）。
