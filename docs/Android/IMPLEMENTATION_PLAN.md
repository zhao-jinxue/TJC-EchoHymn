## 一、执行原则（先定规则，再定任务）

| # | 原则 | 说明 |
| --- | --- | --- |
| 1 | **工单化** | 每个工单（WP）能在**一个会话**内完成并验收；一个会话内最多 2 个工单 |
| 2 | **先验收后前进** | 工单的验收命令**全绿**才允许进入下一个；不允许"先欠着" |
| 3 | **状态外置** | 会话内的一切进展**必须**落到 `STATE.md` + git 提交；聊天记录不作为凭据 |
| 4 | **按需读文档** | 开发计划按**章节**读（`start_line/end_line`），不整读；历史会话日志**只读最近 1 条** |
| 5 | **证据留档** | 每个工单留：命令输出摘要 / 截图（`_shots/android/`）/ 日志（`release/android-release.log`） |
| 6 | **桌面不退化** | 任何共用代码改动后，跑 `flutter analyze` + `flutter test` + Windows 实机关键路径 |

## 二、上下文预算模型（回答"会不会没余地"）

**实测基线**（本项目）：MCP 精简后会话基础 **≈22K tokens**；`ANDROID_PLAN` **≈78K**；`UI_CONFIRMATION_ANDROID` **≈25K**；单条会话日志最大 **≈38K**；45 条日志合计 **≈390K**。

**每会话预算（按 200K 上限）**

| 项 | 预算 | 说明 |
| --- | --- | --- |
| 系统提示 + 规则 + MCP（≈2 个轻量） | ≈22K | 固定成本，已优化 |
| `STATE.md` | ≤2K | 唯一续接入口 |
| 本文「当前阶段」一节 | ≤3K | 按节读 |
| `ANDROID_PLAN` **当前阶段相关章节** | 3~8K | 按章节读（如 A 阶段只看 §4.2 + §1.1 + §2.2） |
| 上一条会话日志的「最终结果」段 | ≤2K | **不读全文** |
| `git log -3` + `git status` | ≤1K | — |
| **启动合计** | **≈33~38K（17~19%）** | 余 **160K+** 给开发 |
| 工作区（读代码 / 改代码 / 跑测试 / 写日志） | ≤120K | — |
| 安全余量 | ≥40K | 低于此值**必须准备收尾** |

**硬阈值（触发即行动）**

| 信号 | 动作 |
| --- | --- |
| 上下文使用 > **60%** | 停止新工作，把当前进展写入 `STATE.md`，提交 |
| 压缩（compaction）发生 **1 次** | 立即对照 `STATE.md` 复核（压缩后细节会丢） |
| 压缩发生 **2 次** | **结束会话**，按 §四 轮换 |
| 连续 **2 个工单无实质进展** | 结束会话，把阻塞点写进 `STATE.md` |
| 单文件 > **500 行** 且需查阅 | 用 `start_line/end_line` 或 `grep` 定位，不整读 |

**结论**：只要按上表执行，**不会出现"资料太多没余地"** —— 因为每次只加载"状态 + 当前工单 + 当前章节"（≈35K），而不是"全部文档 + 全部历史"（>390K）。

## 四、Agent 会话策略（是否切换 / 压缩后怎么继续）

### 4.1 直接答案

| 问题 | 答案 |
| --- | --- |
| **需要切换会话吗？** | **必须切**：一个会话只做 **1~2 个工单**；里程碑结束或压缩 2 次即强制轮换 |
| 不切会怎样？ | 历史代码 + 日志占满上下文 → 后期只能"读"不能"改"（正是你担心的情况） |
| 切换后怎么保证继续？ | **`STATE.md` 是唯一真相**（不是聊天记录）+ git 提交 + 最近 1 条会话日志 |
| 压缩（compaction）后怎么保证？ | 压缩后**立刻**读 `STATE.md` 与 `git status`，用磁盘事实覆盖记忆；**禁止凭记忆改文件**，先 `grep` 验证 |
| 会话日志要读几条？ | **只读最近 1 条**的「最终结果」段（历史 45 条合计 ≈390K tokens，绝不整读） |

### 4.2 切换时机（三档）

| 档 | 触发条件 | 必做动作 |
| --- | --- | --- |
| **A 常规轮换** | 一个里程碑完成（M1/M2/…） | 更新 STATE（阶段完成 + 下一工单）→ 更新开发计划 §十 状态 → 提交 → 写会话日志 → 开新会话 |
| **B 强制轮换** | 上下文 >60% · 或压缩 2 次 · 或连续 2 个工单无实质进展 | 同 A，并在 STATE「阻塞」写原因与建议下一步 |
| **C 紧急收尾** | 上下文 >80% · 或工具连续失败 | 只做三件事：写 STATE → `git add -A && git commit` → 写会话日志（列未完成事项） |

### 4.3 会话收尾清单（离开前 5 分钟逐条打勾）

- [ ] `STATE.md` 更新：阶段 / 最后完成工单 / **下一工单** / 阻塞 / 验收命令
- [ ] `git status` 干净（代码与文档都已提交）
- [ ] 会话日志已写：**改了什么 / 验证了什么 / 遗留什么**
- [ ] 若改过共用代码：`flutter analyze` 0 + `flutter test` 全绿
- [ ] 证据留档（截图 / 命令摘要，可选）

### 4.4 会话启动清单（新会话第一件事，≤5 分钟）

1. 读 **`STATE.md`**（≤2K）：阶段 / 下一工单 / 阻塞
2. 读本文件「三、阶段与工单」**当前阶段那一节**（≤3K）
3. 按 STATE 的"必读章节"读 `ANDROID_PLAN.md` 的**相关章节**（`start_line/end_line`，不整读）
4. 读**最近 1 条**会话日志的「最终结果」段（≤2K）
5. `git log --oneline -3` + `git status --short`
6. 用 **≤5 行**汇报：当前阶段 / 上一工单结论 / 本次工单 / 阻塞 → 等待确认

> **禁止**：读全部会话日志、整读 `ANDROID_PLAN`、读 `release/`、`data/`、`docs/ruanzhu/`、`docs/Windows/*` 全文（见 §五）。

### 4.5 压缩后恢复协议（关键）

压缩会丢**推理过程与已读细节**，但不会丢磁盘上的东西。因此：

1. 压缩后**第一件事**：读 `STATE.md` + `git status` + `git log -3`
2. **任何"我记得某处是…"的判断，先 `grep` 验证**（压缩后记忆不可信）
3. 重建最小上下文：STATE + 当前工单 + 目标文件的 `grep` 命中片段（不要重新整读）
4. 压缩 2 次仍无法推进 → 按 B 档轮换
